# ② 拆模块：从核心循环里长出模块，而不是先想类名

> **文件用途**：流程第二阶段的作业规范——把拆清楚的需求变成一组边界明确的模块。
> **创建时间**：2026-08-30
> **来源**：【AI研发闲聊】423《如何把一个游戏想法拆成可开发模块》

---

## 一、第一步不是想类名，是写核心循环

**常见错误**：一上来讨论"要建哪些文件夹""类名叫什么"。

类名和脚本结构是**后面实现时才慢慢定下来的**。如果连一局游戏怎么开始、怎么推进、怎么结束都还没说清楚，AI 会先给你搭一堆看起来完整的脚本，但真正接功能时全对不上。

**正确做法**：先写"玩家一局里反复在做什么"。

```
进入关卡
敌人按波次出现
玩家用金币建塔
塔攻击敌人
敌人死亡掉落金币
敌人到达终点扣血
清完波次胜利 / 基地血量归零失败
```

循环写出来，模块就**自己露出来**了：
敌人按波次出现 → 波次系统；建塔 → 建造系统 + 资源系统；塔攻击 → 塔系统 + 索敌 + 子弹；到达终点扣血 → 路径系统 + 基地血量；清完波次 → 战斗状态 + 结算系统。

## 二、模块不是越多越好

**过度架构是早期原型的头号杀手。** 如果你一开始就让 AI 按这种方向写：

```
寻路服务 / 索敌服务 / 战斗事件总线 / 伤害结算管线 / Buff 管理中心 / 关卡生命周期控制器
```

它会生成一堆看起来很专业的代码——文件很多、接口很多、抽象很多，**但真正跑起来的东西不多**。

**判据**：第一版只拆「能支撑核心循环的**最少**模块」。真的需要 Buff 了，再加 BuffSystem；真的需要天赋了，再加 TalentSystem。

> 项目早期最重要的是**先跑通**，不是先摆出一个很完整的架子。

## 三、边界比名字重要：回答这五个问题

列几个模块名不算拆完模块。真正重要的是回答"谁能改谁的数据"：

| 问题 | 典型错误答案 |
|---|---|
| 塔能不能直接改敌人血量？ | 能（短平快，但伤害类型/护盾/反弹全没法加） |
| 命中时由谁计算伤害？ | 谁方便谁算（结算顺序会失控） |
| 敌人死亡由谁通知资源增加？ | 敌人自己（表现与逻辑耦合，死亡动画/分裂/爆炸全崩） |
| UI 能不能直接改资源？ | 能（状态源头变多个，跨天续局时对不上） |
| 子系统能不能直接判定胜负？ | 能（胜负条件散落各处，加一个条件要改 N 处） |

### 反面案例：一个 Update 干五件事

```
Tower.Update:
    target = find nearest enemy     # 索敌
    target.hp -= damage             # 扣血
    if target.hp <= 0:
        player.gold += reward       # 发奖励
        destroy target              # 销毁
```

小 Demo 能跑。但要加子弹飞行、护盾、伤害类型、死亡动画、掉落物、统计数据时，这段逻辑很快改不动。

**更稳的分法**：塔只负责找目标和发起攻击；子弹只负责飞行和命中；敌人自己处理血量和死亡；奖励由战斗状态或奖励模块处理。

## 四、先拆数据，再拆逻辑

**很多系统看起来是逻辑问题，其实是数据没拆。**

顺序固定：

```
TowerData:                      TowerLogic:
  towerId                         查找目标
  attackRange / attackInterval    判断冷却
  damage / bulletId               发射子弹
  targetRule                      升级
  buildCost / upgradeCost         刷新表现
```

**不先拆数据的后果**：AI 把数值写死在脚本里（`damage = 10`）。第一天很方便，然后——加第二种要复制一份脚本；调数值要改代码；想让表驱动就得重构。

### 让 AI 先整理数据结构的提示词

```
请先不要写代码。
我在做【项目类型】，请帮我整理第一版需要的数据配置。
按【A / B / C / D / E】五类整理。
每类只列第一版真正需要的字段，不要扩展太多。
```

数据结构一旦定下来，后面的代码就有了方向。

## 五、模块之间别互相乱改数据

约定**唯一的写入口 + 只读监听**，第一版不需要复杂事件总线，这么写就够了：

```
BattleState:                     BuildSystem:
  gold                             if BattleState.SpendGold(cost):
  AddGold(amount)                      create tower
  SpendGold(amount)
  OnGoldChanged                    BattleUI:
                                     listen OnGoldChanged → refresh
```

金币归 `BattleState` 管；UI 只显示；建造系统只**申请**花钱；其他系统不随便改金币。

这类约定看着很小，但对 AI 帮助极大——它知道该调用什么，**不该越界改什么**。

## 六、运行逻辑与表现逻辑分开

一个"敌人死亡"其实是两件事：

| 逻辑层 | 表现层 |
|---|---|
| 血量归零、停止移动、从列表移除、发出死亡事件 | 播放动画、掉落特效、飘字、音效、延迟销毁模型 |

混在一起的后果：有些敌人死亡后要分裂、有些要爆炸、有些动画播完才消失、有些是逻辑死亡本地延迟表现——全都改不动。

> **写任务单时直接把话说清楚**：
> "本次只实现死亡逻辑，表现只保留一个简单销毁，不做动画和特效。**不要把金币、UI 刷新写进 EnemyBase。**"

## 七、不同游戏，模块拆法不同——不要套模板

塔防的核心是路径、建塔、波次；弹幕互动战斗的核心是事件输入、刷兵、战斗规则、前后端同步；视错觉解谜的核心是玩家移动、视角旋转、视觉连通判断。

**方法不是套模板，是回答同一组问题**：

1. 玩家反复做什么？
2. 系统反复判断什么？
3. 哪些数据会变化？
4. 哪些东西需要显示？
5. 哪些东西要保存？

**本项目类型的答案**见 [06-项目类型适配.md](06-项目类型适配.md)——它的核心循环和塔防完全不同，模块会长成另一个样子。

## 八、拆完不要马上全做：打通一条最短链路

拆出八个模块 ≠ 八个同时开工。**同时开工的结果通常是每个都写了一半，整体跑不起来。**

正确顺序是选一条能跑通核心循环的**最短链路**，一步一步串起来，跑通后再补 UI、配置表、升级、特效、音效。

```
第一步：敌人能沿路径移动
第二步：波次能生成敌人
第三步：塔能锁定敌人
第四步：塔能造成伤害
第五步：敌人死亡后给金币
第六步：敌人到达终点扣血
第七步：胜负能判断          ← 到这里核心循环闭环
```

> AI 开发尤其要注意：它单个任务做得快，但你同时给太多方向，它很可能每块都写一点，最后接不起来。

## 九、模块边界卡

每个模块产出一张卡，模板见 [../assets/模块边界卡模板.md](../assets/模块边界卡模板.md)。三要素缺一不可：

```
负责：      这个模块独占的职责
不负责：    ★ 最容易漏，也最有价值——明确划出去的职责
依赖：      它调用谁 / 谁调用它 / 数据来源
```

## 十、检查表

- [ ] 核心循环已写出（不是类名清单）
- [ ] 模块数是「支撑核心循环的最少数量」，无提前加入的未来系统
- [ ] 五个边界问题（谁改谁的数据）已回答
- [ ] **数据字段先于逻辑清单**产出
- [ ] 模块间通信走约定接口，无互相直接改数据
- [ ] 逻辑层与表现层已分开，且任务单里写明
- [ ] 每个模块有边界卡，「不负责」非空
- [ ] 已选定最短链路，非全模块并行
