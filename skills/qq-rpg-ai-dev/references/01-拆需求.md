# ① 拆需求：把想法拆成"AI 不需要猜"的问题

> **文件用途**：流程第一阶段的作业规范——把一句模糊的游戏想法，拆成一组必须回答的问题，并划出四层范围。
> **创建时间**：2026-08-30
> **来源**：【AI研发闲聊】414《先让 AI 帮你拆需求，而不是直接让它开工》、410《AI 做游戏，第一步不是写代码》

---

## 一、为什么先拆需求

"我想做一个肉鸽塔防""我想加一个召唤流职业"——这类话用来聊天没问题，**用来派活就是灾难**。

因为里面几乎每个词都对应很多种完全不同的实现：

| 词 | 可能的含义（互不相容） |
|---|---|
| 回合制 | 行动条？CTB？纯轮次？我方全体行动完才轮到敌方？ |
| 随机 | 随机地图 / 随机奖励 / 随机敌人 / 随机词条？局内还是局外？有无保底？ |
| 职业 | 绑武器还是不绑？专属资源还是共用怒气？能否跨职业带战技？ |
| 托管 | 离线自动打到结束？只托管 N 回合？托管时用不用战技？ |

你不说，AI 就按"它脑子里默认的版本"补。补对了像很懂你，补错了就是持续返工。

## 二、核心动作：让 AI 只拆问题，不写代码

**最关键的一句提示词：**

> 请你**先不要写代码**。

不加这句，AI 会本能地往代码上走——你只是想讨论方案，它已经开始给你生成类、接口、方法了。需求还没定，这些代码反而干扰判断。

### 可直接复用的提示词模板

```
我想做一个【一句话描述玩法】。

请你先不要写代码。
先帮我把这个想法拆成开发前必须确认的问题，按下面几类整理：
1. 核心玩法
2. 【本项目的关键子系统，如：战斗流程 / 指令与交互 / 数值与成长】
3. 数据结构
4. 【本项目的关键子系统，如：异步与托管 / 推送与战报】
5. UI 与结算
6. 后续扩展风险

每一类只列真正会影响开发结构的问题。
不要给出完整策划案，不要列所有可能性。
```

**模板的重点不在"帮我拆需求"，而在后面的限制。** 不卡范围，AI 会给你一份几万字、什么都考虑一点、但你仍然不知道第一步做什么的文档。

## 三、拆到什么程度停：拆到能开工

**拆需求不是越细越好。** 目标是"能开工"，不是"穷尽所有可能"。

判断标准：这份问题清单回答完，能否直接写出第一版任务单？能，就停。

第一版**不应该**讨论的东西（典型）：赛季系统、排行榜、皮肤、复杂天赋树、多章节剧情、新手七日目标、社交。这些先放后面。

## 四、四层范围表（核心产出）

不要把所有需求平铺，强制分层：

| 层 | 含义 | 判断问题 |
|---|---|---|
| **L1 · DEMO 必须有** | 缺了核心循环跑不起来 | 砍掉它，"这一局"还能不能玩？ |
| **L2 · 第一版可以有** | 显著提升完整度，可延后 | 砍掉它，游戏还完整吗？ |
| **L3 · 后续版本再考虑** | 有价值但依赖前置 | 现在做会被将来推翻吗？ |
| **L4 · 现在明确不做** | 主动放弃 | 不写进来，AI 会顺手做吗？ |

> **L4 是四层里最重要的。** AI 很擅长补全——你说要做"关卡系统"，它可能顺手给你加上关卡解锁、星级评价、章节分页、存档记录、奖励结算、UI 动画、关卡预览图、失败重试。
> 每一项单看都合理，但都不是你这次要的。更糟的是，它会为实现这些**顺手改掉已有结构**。

## 五、还要拆"玩法需求"和"工程需求"

很多话听着是玩法问题，落到开发里全是工程问题。

**例子**："塔可以升级" → 开发时要继续拆：

- 局内升级还是局外升级？（玩法）
- 升级数据从哪读？（**工程**）
- 升级后是否影响已经发出去的子弹？（**工程 + 边界**）
- 升级消耗金币还是材料？（玩法 + 数据）
- 哪些地方要刷新？（**工程**）

**这类项目尤其要拆的工程问题**：

| 工程问题 | 为什么在本项目要命 |
|---|---|
| 数据从哪里读 | 数值必须进常量表，一个数字只住一个地方；硬编码会让跨文件联动失控 |
| 状态存在哪里、跨不跨天 | QQ 群跨天单实例，状态要能持久化并能"续" |
| 玩家不在线时谁决定行动 | 托管/超时托管的代打规则必须先定，否则异步链路写不出来 |
| 战报怎么渲染 | 战报是唯一表现出口，逻辑层不该关心文案；塞多了就刷屏 |
| 哪些地方要刷新 | 断线重连、跨天续局时，刷新遗漏 = 状态错乱 |

## 六、推荐的六步实操流程

```
1. 把想法写成一段普通描述（像跟朋友解释一样，不用正式）
        ↓
2. 让 AI 只拆问题，不写代码
        ↓
3. ★ 人做选择（这一步不能交给 AI）
        ↓
4. 让 AI 把结论整理成四层范围表
        ↓
5. 让 AI 挑刺：审查这份需求本身
        ↓
6. 产出任务单（→ 03-任务单.md）
```

### 第 5 步"让 AI 挑刺"的提示词

```
请你先不要写代码，只审查这份需求说明。重点看：
1. 有没有描述不清的地方？
2. 有没有容易导致结构混乱的地方？
3. 有没有后续扩展会踩坑的地方？
4. 有没有本阶段不该做、却被提前写进去的内容？
5. 哪些地方需要补充验收标准？
```

这一步的价值：把自己脑子里**默认的前提**翻出来。你知道"敌人路径是 Tilemap 预设的"，但需求里没写——AI 不知道。

挑出来的问题不一定都改，但这个过程通常很值。

## 七、检查表（派活前逐项确认）

- [ ] 问题清单已按类整理，且**不写代码**的约束已写明
- [ ] 四层范围表齐了，L4「明确不做」**非空**
- [ ] 玩法需求和工程需求**都**拆了（数据/状态/异步/刷新四项已回答）
- [ ] 已让 AI 挑过一次刺，并记录采纳/忽略的理由
- [ ] 能直接据此写出第一版任务单

## 八、本阶段的反面案例

❌ **"帮我做一个塔防游戏。"** — 太大，AI 只能猜。

❌ **"帮我生成完整游戏设计文档。"** — 会产出一份很大、很全、但不知道第一步做什么的文档。

❌ **只写"做什么"，不写"不做什么"。** — AI 会把一个小功能扩成一套系统。

❌ **让人（或 AI）在第 3 步替你做选择。** — 选择权是你在这个流程里不可替代的价值。
