# ③ 任务单：让 AI 不需要猜，也不允许顺手做

> **文件用途**：流程第三阶段的作业规范——把拆好的需求写成一份有边界的任务单，这是唯一适合直接交给 AI 执行的形态。
> **创建时间**：2026-08-30
> **来源**：【AI研发闲聊】410《AI 做游戏，第一步不是写代码》、535《AI 开发项目里，文档反而更重要了》

---

## 一、为什么必须写任务单

一大段需求文档丢给 AI，它也会抓不住重点。**任务单要短、边界要清楚。**

更关键的是：**"不要乱改其他代码"对 AI 来说没有统一标准。** 你觉得顺手抽一个接口属于乱改，它可能觉得这是正常优化。

所以任务单必须把范围**显式列出来**。

## 二、九要素（缺一不可）

| # | 要素 | 说明 |
|---|---|---|
| 1 | **本次要做** | 编号列出，每条一个原子改动 |
| 2 | **本次不做** | ★ 最容易漏，也最有价值 |
| 3 | **已有结构** | 现有模块/文件及其职责，让 AI 复用而不是重造 |
| 4 | **允许新增** | 精确到文件名 |
| 5 | **允许修改** | 精确到文件，越窄越好 |
| 6 | **禁止修改** | ★ 精确到文件/接口，写明"为什么不能动" |
| 7 | **输入 / 输出** | 输入数据结构、预期产出物形态 |
| 8 | **规则** | 本次必须遵守的玩法规则（数值来源、结算顺序、边界条件） |
| 9 | **验收** | 可判定的通过条件，含**回归项** |

## 三、对比：差任务单 vs 好任务单

### ❌ 差

```
帮我做一个减速塔。
```

太短。AI 能做，但会自己发挥：可能在敌人脚本里加 `isSlow`，可能在命中时直接改速度，甚至顺手把塔、子弹、敌人的结构都改了。

### ✅ 好

```
请基于现有 TowerBase、EnemyBase、BulletBase 三个脚本，实现一个减速塔。

要求：
1. 减速塔使用 TowerSlow.cs。
2. 子弹使用 SlowBullet.cs。
3. 子弹命中敌人后，给敌人添加持续 2 秒的减速效果。
4. 减速比例从 TowerData.slowRatio 读取（0.3 = 速度降低 30%）。
5. 不要直接修改 EnemyBase 的移动主逻辑。
6. 只通过 EnemyBase.ApplyMoveSpeedModifier() 接口影响速度。
7. 不要改动已有普通塔的攻击逻辑。
8. 完成后说明需要挂载哪些组件、要配置哪些字段。

验收：
- build SlowTower → 敌人进范围 → 塔发射 SlowBullet
- 命中后 currentSpeed 按 slowRatio 降低
- 2 秒后速度恢复
- 普通塔逻辑不受影响          ← 回归项
```

**差别在于：前者没有边界，后者每一条都在收紧边界。**

## 四、"不做什么"是主角

AI 很擅长补全，**经常会把一个小功能扩成一套系统**。

但真实开发里，很多时候只想先补当前缺的那一块，让项目能继续往下走——不需要每次都顺手开一个大系统。

**典型禁止项（按项目类型给的默认清单）**：

```
不能修改：
- 内核层任何文件（内容 ID 不允许出现在内核）
- 常量表的既有键名（只能新增键，不能改名/删除）
- 已发布职业卡的既有数值段
- 战报模板的行数上限（防刷屏）
- 存档结构 / 协议格式
```

## 五、规则段要写清"边界条件"

规则段最容易漏的是**边界条件**。一个真实例子：

> "塔升级后只影响之后发起的攻击，**不追溯已经发射出去的子弹**。"

这句话是为了避免已经飞出去的子弹因为塔升级而突然改变伤害。这种细节不说，AI 通常按最省事的写法处理。

**本项目的高频边界条件**（写任务单时逐条考虑）：

| 类型 | 要写清什么 | 漏了会怎样 |
|---|---|---|
| 频率/段数类 | 是"+N 次"还是"+N 次/回合"？是否跨回合累积？ | 二阶放大，单点看着平衡，整周期崩 |
| 削减类 | **方向**：是"抗性 −x"还是"易伤 +x"？ | 数值写反，效果完全相反 |
| 持续类 | 持续时间按谁的回合算？跨阶段保留吗？ | 状态错乱 |
| 触发类 | 同一回合多次触发如何处理？ | 无限循环或漏触发 |
| 异步类 | 玩家离线时该效果如何代执行？超时怎么算？ | 托管结果与在线不一致 |

## 六、本项目专属：改任何数值前的三步自查

> 引自 `README.md`（源自 `14` 三条通律），**动数值前必须逐条过**：

> ① 涉及「加速 / 频率 / 段数 +N」→ **必须重跑完整周期 ΣM/回合**，不能只看单点；
> ② 涉及辅助职业 → 确认它有**把资源换成自己伤害的出口**；
> ③ 涉及「削减」类词汇（硬度 / 抗性）→ 确认**方向**，H 是伤害乘区，值越大越好打。

**这三条是真实事故换来的**，尤其第③条——本项目曾因「部位硬度」这个中文名与 H 的实际语义（伤害乘区，值越大越好打）相反，导致三处独立 bug：疲态期本该更好打却写成了更难打、破甲突本该无视护甲却让硬部位更硬。

## 七、本项目专属：三条减法（绝不做）

> 引自 `02_职业×流派×武器解耦.md` §2.4.5：

> ① 不下调已发放倍率；
> ② 不削已发放符文 / 专械 / 超限阶位；
> ③ 不删改任何战技变体、职业与武器。

**补偿弱组合的正确做法是加法**：加机制、加变体、加环境，而不是削弱别人。

> 任务单里如果出现了"下调某数值以对齐"这样的措辞，直接打回。

## 八、验收段要包含回归项

验收不只是"新功能能用"，还必须包含**"没碰坏旧的"**：

```
验收：
1. 【新功能】……正常生效
2. 【边界】……超时/不足/重复触发时的表现符合规则段
3. 【回归】原有 XX 逻辑不受影响        ← 必写
4. 【回归】无 XX 的对象行为不变        ← 必写
```
