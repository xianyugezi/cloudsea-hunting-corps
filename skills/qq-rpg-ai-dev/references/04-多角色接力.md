# ④ 多角色接力：让每个 AI 都在做同一个项目

> **文件用途**：流程第四阶段的作业规范——用「分析 → 实现 → 审查」三角色推进，并规定何时可以并行、如何定文件归属、谁拍板。
> **创建时间**：2026-08-30
> **来源**：【AI研发闲聊】523《多 Agent 协作开发：从角色分工到工程落地》

## 一、多个 AI 不会自动变成一个团队

多开几个 AI，各自写得都挺完整，放一起却接不上——**因为任务边界、项目文档、接口和代码状态没有统一。**

多 AI 协作真正要解决的，不是"要几个角色"，而是**这些角色怎么围绕同一个项目工作**。

## 二、一开始不需要真的上很多 Agent

不要一上来搭一套"需求 Agent / 程序 Agent / 数值 Agent / 测试 Agent / 审查 Agent / 项目管理 Agent"自动讨论的复杂系统。

**先做分阶段的多角色工作流**——哪怕还是同一个 AI，只要不同阶段使用**独立上下文 + 不同任务目标**，就已经能得到大部分收益：

```
阶段一（分析）：你现在只负责需求分析。不要写代码。请把这个系统拆成……
阶段二（实现）：你现在负责实现。下面是已确认的需求和现有结构。
                 请只根据这些内容设计结构，不要自行增加新玩法。
阶段三（审查）：你现在只负责审查。不要重写代码。重点检查……
```

对个人或小团队，先把「分析 / 实现 / 审查」分开，已经能解决很多问题，而且**更容易控制**。

## 三、为什么必须分开角色

**一个 AI 从头做到尾，会越来越沿用自己前面的判断。**

真实例子：设计 Buff 系统时它默认"同类 Buff 可以叠加"；后面写代码沿用这个规则；再让它审查时，它只会检查"代码有没有正确实现前面的设计"，**不会重新追问"同类 Buff 真的应该叠加吗"**——因为这个前提就是它自己定的。

角色分开后，审查者拿到的是**已确认的规则**，再去对照代码，就容易发现偏离。

### 但角色分离不能保证正确

如果几个角色使用同样的模型、拿到相似的上下文，或者**原始需求本身就是错的**，它们仍然可能犯同一种错误。

> 角色真正的价值，是让不同阶段**关注不同问题**：一个负责完成，一个负责挑错，一个负责验证。
> 不是增加赞成票。

## 四、角色边界比角色名字重要

叫它"高级程序架构师""首席测试工程师"没有意义。**真正影响结果的是：职责 / 不能做 / 输出。**

| 角色 | 职责 | 不能做 | 输出 |
|---|---|---|---|
| **分析** | 把模糊想法拆成问题；指出缺失信息与潜在风险 | 不写代码；不做技术选型 | 问题清单、四层范围表、风险提示 |
| **实现** | 按已确认任务单写代码/配置/文档 | 不改玩法规则；不自行新增系统；不改存档协议；不做无关重构 | 改动说明、文件清单、自检结果、测试建议 |
| **审查** | **独立**对照原始规则检查实现 | 不重写模块；不改需求；不加"更漂亮"的架构 | 必须改 / 建议改 / 需人工确认（三档） |

> 如果只是分别告诉两个 AI"你是一名资深工程师"，它们最后还是会做差不多的事。
> **角色的区别，必须体现在任务边界里。**

## 五、接力，而不是同时开干

```
需求 → 实现 → 审查 → 测试
```

**多 AI 协作不一定意味着并行。** 对开发来说，串行接力反而更稳：上一阶段产出确认后再交给下一阶段，问题容易定位，修改范围容易控制。

### 审查阶段的关键技巧：别让审查者看到实现者的解释

如果审查者读到了实现者的说明，它容易**顺着前一个角色的解释继续往下想**，而不是独立判断。

给审查角色的输入只要三样：

```
原始任务单  +  改动后的代码  +  必要的项目背景
```

### 审查提示词

```
请独立审查这套实现。优先寻找：
1. 与原始需求不一致的地方。
2. 代码自行补充、但需求没有定义的规则。
3. 能构造出失败结果的边界情况。
4. 超出任务范围的修改。
5. 可能导致回归问题的地方。

如果没有证据支持问题，不要为了挑错而强行提出问题。
```

**最后一句很重要**——否则审查角色为了显得有用，会硬凑问题。

## 六、什么时候可以并行

适合并行：**边界清楚、共享接口确定、文件冲突少**的任务。

不适合并行：多个 AI 同时修改同一套核心代码。典型事故——

```
战斗角色：public int CurrentHp;
UI 角色  ：public ReactiveProperty<int> CurrentHp;
重构角色 ：private int currentHp; public int CurrentHp => currentHp;
```

三种写法单看都行，合并时很麻烦。

### 并行前必须明确三件事

1. **文件归属**：谁只能改哪些文件
   ```
   Agent-A：只修改 WaveSystem 和波次配置
   Agent-B：只修改 BattleUI
   Agent-C：只做审查，不修改任何文件
   ```
2. **公共接口**：接口提前定死，后续角色都围绕它开发，不要各自重新设计
3. **物理隔离**：配合独立 Git 分支 / worktree / 独立工作区，最后统一 review 合并

## 七、最后要有人拍板

多个角色意见不一致时，**不能让 AI 无限讨论下去**。

> 项目当前是什么阶段，往往比"哪个架构更完整"更重要：
> 原型期 → 最简单实现可能就够了；
> 长期运营 → 扩展能力更重要；
> 临近上线 → 风险控制比结构漂亮更重要。

AI 可以列出利弊，但它不知道你愿意为一个架构投入多少时间，也不知道哪些未来需求真的会发生。

**在个人/小团队开发里，这个决策者就是你。** 你需要维护：项目当前规则、已决定的方案、不能动的接口、本次任务做到什么程度停。

> 一个角色提方案，一个角色独立检查，一轮之后信息够了就该由人决定。
> 讨论得更久，不代表结果更好，很多时候只是让上下文越来越长、建议越来越多。

## 八、从三个角色开始

```
分析（拆需求、指风险）
   ↓
实现（按任务单执行）
   ↓
审查（独立对照 + 回归清单）
```

测试先并到审查角色里。跑顺以后，再按需要增加数值、关卡、测试、文档角色，或真的引入多个实现 Agent 并行。

## 九、本项目类型的落地

### 9.1 文件归属的既有惯例

| 场景 | 归属规则 |
|---|---|
| 职业数值卡 | **一个职业一个文件**（`13_职业数值卡/NN_职业名_English.md`），子 agent 之间零文件冲突 |
| 全局常量 | 只有 `12_全局常量表.md` 的维护者可改；其他 agent 只能**新增**键，不能改名/删除 |
| 核验类 agent | **一律只读**，输出 PASS/FAIL + 命中清单，禁止顺手修正 |

### 9.2 已验证的并行模式

本项目实际跑通过两次，可作为模板复用：

**模式 A · 内容批量生成（写）**
14 个职业卡 → 14 个子 agent 各写各的文件，零冲突；每卡统一九段结构 + 附 A/B/C，便于后续机器核验。

**模式 B · 变更核验（读）**
一次全局改名后，派 4 路**只读** agent 并行核验：

| agent | 核验域 |
|---|---|
| A | 改名完整性（全库搜旧名 + 权威位置新名到位） |
| B | 新增内容正确且仅为占位 |
| C | 构建与路径一致性（脚本可重建、无陈旧引用） |
| D | 总索引与交叉引用一致性 |

要点：每个 agent 的核验域**互不重叠且合起来覆盖全部**；一律只读，避免多个 agent 同时改同一文件；统一输出 `PASS/FAIL + 命中清单`。

### 9.3 派活提示词必须包含的五段

```
1. 背景：项目是什么、刚发生了什么改动
2. 你的核验/实现域（明确到文件与维度）
3. 明确排除的域（避免与其他 agent 重叠）
4. 只读 / 可写
5. 输出格式与结论词（PASS / FAIL + 具体命中）
```
