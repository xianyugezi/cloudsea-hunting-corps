# ⑤ 项目事实文档：所有角色共享同一份真相

> **文件用途**：流程第五阶段的作业规范——建立并维护"项目当前是什么状态"的共享文档集，这是 AI 能否接得上手的关键。
> **创建时间**：2026-08-30
> **来源**：【AI研发闲聊】535《AI 开发项目里，文档反而更重要了》、523《多 Agent 协作开发》

## 一、AI 最缺的不是代码，是项目历史和边界

AI 能看代码，也能看你的需求，**但它不知道这些东西为什么会变成现在这样**。

真实例子：

```csharp
public void AddGold(int amount) {
    gold += amount;
    OnGoldChanged?.Invoke(gold);
}
```

AI 看到会建议：统一放到 `CurrencySystem`，改成 `Dictionary<CurrencyType, int>`，以后就能同时支持金币、钻石、活动货币，"扩展性更好"。

但也许你早就决定了：**战斗内只有一种临时金币，不带出关卡；钻石和局外货币属于另一套系统，两边就是故意分开的。**

这个决策只存在你脑子里，AI 看不到。于是它把**"项目已经做过的取舍"当成了"还没有完善的地方"**。

## 二、文档要写"不负责"，不只是"有什么"

对每个模块，写清楚负责与不负责：

```
BattleState
负责：
- 当前战斗金币
- 基地 HP
- 胜负状态
不负责：
- 生成敌人
- 播放 UI 动画
- 保存局外货币
- 加载关卡
```

**为什么"不负责"更重要**：AI 写代码时很容易**顺手做完**——

> 敌人死亡了，它顺手加金币；金币变化了，它顺手刷新 UI；场上敌人没了，它又顺手判断胜利。
> 单独看每一步都合理，最后却把系统边界慢慢写乱了。

## 三、五份共享文档（名字可改，职责不可少）

| 文档 | 记什么 | 谁来更新 |
|---|---|---|
| `PROJECT.md` | 项目结构、技术栈与约束、主要模块清单 | 项目负责人 |
| `GAME_RULES.md` | **已确认**的玩法规则（不是待议） | 规则变更时 |
| `ARCHITECTURE.md` | 模块职责边界 + 公共接口 | 结构变更时 |
| `TASK.md` | 当前任务目标、允许修改范围、验收标准 | 每个任务 |
| `DECISIONS.md` | **为什么**这么定 + 重评估条件 | 每次拍板 |

模板见 [../assets/项目事实文档集/](../assets/项目事实文档集/)。

## 四、别让规则散在聊天记录里

同一条规则经常是**在不同时间慢慢补齐**的：

```
第一次：同类减速不叠加，只刷新持续时间。
做 Boss 时补：Boss 免疫减速。
做第二种减速技能才发现：不同来源的减速取最高值。
```

散在不同对话里，过一段时间连自己都记不清最终版本是哪一个，下一次又要重新解释一遍。

**对策**：已确认的规则放到固定位置，以后一律以那里为准。

```
GAME_RULES.md
## Slow Buff
- 减速使用百分比。
- 同一 Buff 重复命中不叠层，只刷新持续时间。
- 不同来源的减速取最高值。
- Boss 免疫减速。
- 减速免疫不影响伤害结算。
```

## 五、文档最怕的不是少，是旧

> **AI 会非常认真地按照错误信息继续开发。**

假设 `ARCHITECTURE.md` 里还写着"BattleUI 直接读取 GameManager 中的金币"，但代码早就重构成 `BattleState → OnGoldChanged → BattleUI`。

下一个 AI 先读旧文档，就会开始写 `GameManager.Instance.Gold`。**从它的角度看，它没有乱写，反而是在认真遵守项目说明。**

**规则**：

1. 项目规则变化时，**先更新共享文档，再继续下一轮任务**。
2. 文档写得越详细，过期后误导越严重——只保留真正会影响后续开发的内容。
3. 定期用 `scripts/check_docs_freshness.py` 检查文档是否比代码旧。

## 六、让 AI 帮忙维护文档，但要增量更新

```
请根据这次最终代码修改检查 ARCHITECTURE.md。
只更新确实发生变化的部分。
不要重新改写整份文档。
如果代码和文档存在冲突，先列出冲突，不要自行判断哪一个正确。
```

**最后一条最重要**：代码与文档不一致时，AI **不应该自己猜谁是真相**。先列冲突，由人确认。

> 让 AI 重写整份文档是常见陷阱——它会"顺手"把你精心维护的边界声明和决策理由抹平，生成一份漂亮但没有决策信息的文档。

## 七、记录"为什么"：DECISIONS.md

代码能告诉 AI **当前怎么实现**，但很难告诉它**为什么故意这么实现**。

不记录的后果：AI 会反复提出同一个已被否决的建议，然后从头讨论一遍。

```
DECISIONS.md

暂不引入 Addressables。
原因：
- 当前资源规模较小。
- 现阶段主要目标是完成战斗原型。
- 暂时没有远程内容更新需求。
重新评估条件：
- 资源量明显增加。
- 开始做热更新或分包。
```

**三段式：决定 / 原因 / 重评估条件。** 缺了第三段，这份记录会随着时间变成"不知道还适不适用"的死档案。

> 它最大的作用不是证明当初的决定永远正确，而是告诉未来的自己和 AI：**这个问题以前讨论过，当时为什么这么决定**。条件变了再重新评估。

## 八、任务文档直接约束 AI

与其写"帮我增加一个冰冻塔，不要乱改其他代码"，不如直接写：

```
任务：增加冰冻塔。
允许新增：FreezeTower.cs、FreezeBullet.cs
允许修改：BuffConfig.cs
不能修改：TowerBase 公共接口、EnemyBase 移动逻辑、BattleState、存档结构
规则：造成 10 点伤害；附加 30% 减速持续 2 秒；重复命中刷新时间不叠层；Boss 只受伤害不受减速
验收：普通敌人减速正常；Boss 移动速度不变；普通塔逻辑不受影响
```

"不要乱改"对 AI 没有统一标准。**明确列出范围，AI 才知道边界在哪。**

任务完成后，让 AI 顺便检查哪些项目文档需要同步更新——把文档维护接进开发流程，而不是攒着以后补。

## 九、文档不用写成报告

个人/小团队项目没必要为了 AI 写几十页正式说明。**一个模块几行就够**：

```
WaveSystem
负责：
- 读取当前关卡波次。
- 按时间生成敌人。
- 发出波次开始和完成事件。
不负责：
- 判断最终胜利。
- 管理敌人血量。
- 发奖励。
依赖：StageData、EnemySpawner、BattleFlow
```

> 文档是否有用，**不看篇幅，而看下一次开发时能不能减少重新解释**。

## 十、本项目类型的落地映射

| 通用文档 | 本项目对应 | 备注 |
|---|---|---|
| `PROJECT.md` | `README.md` | 目录树 + 索引表 + 阅读顺序 |
| `GAME_RULES.md` | `00_世界观与术语规范.md` + `01_战斗核心系统.md` | 术语与伤害公式的唯一出处 |
| `ARCHITECTURE.md` | `11_架构与模块化规范.md` + `12_全局常量表.md` | 三层架构 + 常量十二域 |
| `TASK.md` | 每次的任务单 | 模板见 `assets/任务单模板.md` |
| `DECISIONS.md` | `14_全局待裁决项与回填记录.md` | W-xx 编号裁决记录 + 回填清单 |

### 10.1 本项目的防漂移机制（值得复制）

**单一数据源原则**：模块分章是唯一真相，单文件合集由脚本从分章**自动重建**，禁止手改合集。

```
13 份分章（手改的唯一入口）
        │
        │  python3 build_collection.py
        ▼
云海猎团_QQ群回合制RPG_PvE设计稿.md   ← 自动重建，头部标注"请勿直接编辑"
```

这一条解决的就是"文档怕旧"——漂移无法复发。本项目曾因手维护合集，导致 7 处已修复的 bug 仍留在合集里。

### 10.2 裁决记录的既有格式（W-xx）

```
| 编号 | 问题 | 裁定 |
|---|---|---|
| **W-05** | 团队增益折算率三卡不一致 | 分档：团队 0.55 / 主控 1.00；诗人豁免 |
```

完整记录应含：**问题 / 裁定 / 理由 / 副作用与处置 / 重评估条件**。模板见 [../assets/裁决记录模板.md](../assets/裁决记录模板.md)。
